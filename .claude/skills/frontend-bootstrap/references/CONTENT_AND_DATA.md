# Content and Data Strategy

A polished interface can still fail when realistic data arrives.

## Use domain-realistic content

Prefer names, labels, values, statuses, and actions that belong to the actual project domain.

Do not use Lorem Ipsum unless the product is literally a text-layout experiment.

## Stress cases

Design/test at least these when relevant:

- very long title/name
- short title/name
- zero value
- negative value
- huge value
- missing avatar/image
- no records
- one record
- many records
- loading
- partial failure
- permission denied
- offline/retry
- long table cell
- wrapped status
- translated content that expands
- mobile keyboard/composer
- 200% browser zoom where practical

## Demo data

FAST LAB demo data should tell the demo story.

Example:
- dashboard: one good trend + one issue requiring attention
- RAG: one query with credible citations
- chat: one conversation that demonstrates context
- admin: mixed statuses and at least one edge case

Demo data should make product value legible, not merely fill empty boxes.

## Copy hierarchy

Use:
- action labels that describe the action,
- domain terms users recognize,
- concise helper text,
- error messages that explain recovery.

Avoid:
- "Learn more" when a specific action exists,
- generic "Something went wrong" if a cause is known,
- fake enterprise jargon.
